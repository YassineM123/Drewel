# Drewel Notification Sound System

The Drewel app plays its own branded sounds ("Drewel audio identity") for every
real-time event: ride requests, driver arrival, messages, calls, warnings and
successful actions. All audio is centralized in one service so events that reach
the app through multiple sources (socket, REST poll, foreground panel) always
produce exactly **one** sound.

The app supports optional FCM push (`lib/common/push_notification_service.dart`).
When Firebase is configured the backend delivers pushes and the app shows local
notifications; without it the app degrades gracefully to socket-driven
notifications (`notification:new`, `call:state`, `ride:state`,
`driver:contact`, `conversation:updated`, `points:*`). In-app audio is
independent of push and works either way.

---

## The 7 branded sounds

| File | Plays for | Length | Vibration pattern |
| --- | --- | --- | --- |
| `drewel_notification.wav` | generic / default notification | ~0.5 s | subtle 40 ms |
| `drewel_message.wav` | chat / ride messages (`RIDE_MESSAGE`) | ~0.3 s | subtle 40 ms |
| `drewel_ride_request.wav` | new ride request to a driver (`driver:contact`) | ~0.8 s | repeating 220 ms pattern |
| `drewel_driver_arrived.wav` | driver arrived (passenger, `ride:state`) | ~0.8 s | double 140 ms pattern |
| `drewel_call.wav` | incoming call ringtone (`call:state`) | ~3.2 s | repeating 500 ms pulse every 1.6 s |
| `drewel_success.wav` | points/trip accepted, points purchased/credited | ~0.7 s | double 70 ms pattern |
| `drewel_warning.wav` | low / insufficient points balance | ~0.6 s | repeating 240 ms pattern |

All files are 44.1 kHz mono 16-bit PCM, peak −3 dBFS, generated by
`tool/generate_drewel_sounds.dart` (re-run that tool to regenerate or replace a
sound).

### Where each file lives (3 copies)

| Location | Purpose |
| --- | --- |
| `assets/sounds/*.wav` | Flutter runtime in-app sounds (`audioplayers`) |
| `android/app/src/main/res/raw/*.wav` | Android OS notification channel sounds |
| `ios/Runner/DrewelSounds/*.wav` | iOS app bundle resources (must also be in the Xcode project) |

Keep the three copies in sync — they are packaged independently.

## Central service: `lib/common/notification_sound_service.dart`

`NotificationSoundService` is created and registered once in `lib/main.dart`:

```dart
final NotificationSoundService soundService = NotificationSoundService();
soundService.init();
Get.put<NotificationSoundService>(soundService, permanent: true);
```

Everything routes through this single `AudioPlayer` instance.

### Public API

| Method | Behaviour |
| --- | --- |
| `init()` | loads prefs, probes vibrator, pre-caches all sounds |
| `playNotification({eventKey})` | generic beep |
| `playMessage({eventKey})` | chat message beep |
| `playRideRequest({eventKey})` | ride-request alert |
| `playDriverArrived({eventKey})` | driver-arrived alert |
| `playSuccess({eventKey})` | success chime |
| `playWarning({eventKey})` | warning chime |
| `playIncomingCall({callId})` | loops the ringtone; one ring per call id; re-invoking with a different id stops the previous ring |
| `stopCallSound({callId})` | stops the ringtone (accept / decline / cancel / expire / gone) |
| `stopRideRequestSound({rideId})` | stops the ride-request alert; suppresses replay for 45 s |
| `stopAllSounds()` | hard stop: ringtone, playback, pending plays, vibration |
| `setSoundsEnabled(bool)` | persisted toggle; disabling silences immediately |
| `setVibrationEnabled(bool)` | persisted toggle; disabling cancels vibration |
| `shouldPlay(key, {window})` | dedup helper: `false` if the key was seen within the window |
| `hadRecentEvent(key)` | `true` if a key was played within its window |

All `play*` one-shot methods are non-fatal: they never throw into the event
pipeline and silently no-op on web/tests/desktop where audio may be unavailable.

### Deduplication & suppression rules

- One logical event can arrive multiple times (socket + REST poll + UI refresh).
  The dedup keys are the `messageId` / `notificationId` / `rideId` / `callId`.
- Default windows: notification 6 s, message 4 s, ride request 45 s,
  driver arrived 25 s, success 6 s, warning 25 s.
- No notification sound is ever played while a call is ringing
  (`isCallRinging` guard).
- `stopRideRequestSound(rideId:)` also records the ride id so the same request
  is not replayed within 45 s.

### Audio contexts

- Normal sounds: Android `sonification` / `notificationEvent` focus, iOS
  `ambient` → respects silent switch & DND.
- Call ringtone: Android `notificationRingtone` focus, iOS `playback` so it
  actually rings.

## Android

### Channels (`android/app/src/main/kotlin/com/drewel/MainActivity.kt`)

Created at app launch. **Channel ids are versioned** — Android persists channel
settings, so changing a channel's sound/behavior requires a **new** channel id.

| Channel id | Sound resource | Vibration |
| --- | --- | --- |
| `drewel_rides` | `drewel_notification` | system default |
| `drewel_ride_requests` | `drewel_ride_request` | pattern |
| `drewel_messages` | `drewel_message` | pattern |
| `drewel_calls` | `drewel_call` | pattern |
| `drewel_system` | `drewel_notification` | system default |

`res/raw` holds the same WAVs; `AndroidManifest.xml` already declares
`POST_NOTIFICATIONS` and `VIBRATE`.

## iOS

The sound files are **bundle resources**, not just Flutter assets. They are
listed in `ios/Runner.xcodeproj/project.pbxproj`:

- `PBXFileReference` + `PBXBuildFile` for each of the 7 WAVs,
- a `DrewelSounds` group under the `Runner` group,
- all 7 entries in the Runner target's `Resources` build phase.

Verify in Xcode: Runner → Build Phases → Copy Bundle Resources lists all 7 WAVs.

## Event → sound wiring

### Realtime notifications (`call_state_controller.dart`, `notification:new`)

`_playNotificationSound` maps the backend `type`:

| Backend `type` | Sound |
| --- | --- |
| `RIDE_MESSAGE` | message |
| `POINTS_LOW_BALANCE`, `POINTS_INSUFFICIENT_BALANCE` | warning |
| `TRIP_OFFER_ACCEPTED`, `POINTS_PURCHASE`, `POINTS_CREDITED`, `PURCHASED_POINTS_CREDITED`, `POINTS_ADJUSTED`, `WELCOME_POINTS_RECEIVED`, `OFFER_POINTS_RELEASED` | success |
| `POINT_PURCHASE_REQUEST_UPDATED` | success when status `approved`/`completed`, otherwise notification |
| everything else | notification |

Other backend types observed: `RIDE_CHARGE`, `TRIP_OFFER_RECEIVED`,
`POINTS_RESERVED`, `RIDE_POINTS_CHARGED`, `TRIP_OFFER_UPDATED`, `WELCOME_BONUS`,
`OFFER_RESERVE`, `TECHNICAL_REFUND` (all fall back to `playNotification`).

### Ride request (`call_state_controller.dart`, `driver:contact`)

Drivers only: `playRideRequest(rideId)`; the same alert is also the
authoritative one — REST refreshes and the UI panel never re-trigger it.

### Ride state transitions (`active_ride_controller.dart`, `ride:state`)

- Leaving `contacting` / `offerPending` → `stopRideRequestSound(rideId)`
- `driverArrived` (passenger) → `playDriverArrived`
- `completed` → `playSuccess`

### Call lifecycle (`call_state_controller.dart`, `call:state`)

- `showIncomingCall` → `playIncomingCall(callId)`
- accept / decline / cancel / expire → `stopCallSound(callId)` (also triggered
  by the REST poll cleanup before local termination)
- App hidden / paused / detached → lifecycle audio stop
- Never plays a notification beep while the ringtone is active

## Testing

```sh
flutter analyze
flutter test
flutter build apk
```

Manual smoke test:

1. Send a ride request (`driver:contact`) → ride-request sound + repeating
   vibration; accept/decline it → sound stops, no replay within 45 s.
2. Receive a `notification:new` of each type → the mapped sound plays once even
   if a REST refresh re-delivers the same event.
3. Trigger an incoming call → ringtone loops; answer/decline → ringtone stops.
4. Enable Silent / DND on iOS → one-shot sounds respect it; the call ringtone
   still rings.
5. Toggle sounds off in settings → all playback and vibration stops immediately.
